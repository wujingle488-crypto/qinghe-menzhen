# 第 2 章 概要设计

## 2.1 设计原则

1. **单 Agent + 工具**：一个大模型主脑负责追问与生成；RAG 是工具，不是并列业务线。  
2. **串行主链路**：理解 → 检索 → 生成 → 门禁，避免「三路并行」误解。  
3. **安全后置且强制**：门禁在 LLM 输出之后，红旗与白名单不可降级关闭。  
4. **组件可缺席**：检索与模型可降级，系统「变笨不能变危险」。  
5. **前后端分离**：React 负责交互与展示；Spring Boot 负责编排、持久化与安全。

┌───────────▼───────────┐   ┌───────────▼───────────────┐

## 2.4 模块划分

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| M1 知识底账与导入 | 病药主数据、科普切段、出处 | 不对用户直接说话 |
| M2 RAG 检索门面 | `retrieve(query)`；混合检索与 RRF 融合；降级 | 不生成最终话术 |
| M3 安全门禁 | 红旗、药白名单、否定语处理 | 不替代 RAG |
| M4 问诊编排 | 单 Agent：追问、调 RAG、生成草稿、过门禁 | 不绕过门禁 |
| M5 就诊卡 | 多卡 CRUD、问诊关联、摘要注入 | 不做诊断 |
| M6 多媒体 | 图片存储与观察、语音转写 | 不自动开药 |
| M7 知识库前台 | 浏览、检索、运营补录 | 不关红旗 |
| M8 前端壳 | 青禾 UI、历史管理、SSE 消费 | 不写医学规则 |

依赖顺序：`M1 → M2 → M3 → M4`；`M5/M6/M7` 并行增强；`M8` 对接全部应用接口。

## 2.5 核心业务流程（概要）

```text
用户输入
  →（可选）Java 快速红旗扫描
  → LLM：判断追问或作答；知识不足则发起 RAG
  → RAG：向量 / 关键词 / 图谱取片段并融合
  → LLM：基于「用户信息 + 片段」生成结构化草稿
  → Java 门禁：红旗？药在白名单？文案是否安全？
  → 通过：返回卡片；不通过：改写为就医建议 / 转人工提示
```

## 2.6 关键数据概要

| 概念 | 存储 | 说明 |
| --- | --- | --- |
| 会话 `cs_session` | MySQL | 含可选自定义标题、状态、更新时间 |
| 消息 | MySQL | user / assistant 轮次 |
| 就诊卡档案 | MySQL | 同一用户多卡；问诊关联 profileId |
| 病 / 症 / 药 / 红旗 | MySQL | 白名单与门禁对照 |
| 文章切段 | MySQL + 向量/ES | RAG 底账与索引 |
| 上传媒体 | 本地 `data/uploads` | 图片 / 语音文件 |

## 2.8 技术选型摘要

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Java 21 + Spring Boot 3.4 | 课程技术栈；适合编排与规则门禁 |
| 前端 | React + Vite + TypeScript | 组件化 UI、SSE 消费方便 |
| 数据库 | MySQL 8 | 事务型底账与白名单 |
| 模型 | OpenAI 兼容（如 DeepSeek） | 追问与生成 |
| 检索 | Chroma / ES / Qdrant / Neo4j（可配） | RAG 内部手段 |
| 推送 | SSE | 展示「检索中 / 生成中」 |

## 2.9 风险与对策（概要）

| 风险 | 对策 |
| --- | --- |
| 模型胡编药品 | 白名单门禁 + 库内文案 |
| 危急漏拦 | 红旗词表 + 预检/后检 |
| 检索服务宕机 | 降级到 MySQL/规则路径 |
| 过期会话号 | 前端识别「会话不存在」并重建 |
| 演示超时 | SSE 超时放宽；流式反馈进度 |
