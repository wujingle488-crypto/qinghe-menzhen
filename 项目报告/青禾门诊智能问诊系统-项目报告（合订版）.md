# 第 1 章 需求分析

## 1.1 项目背景

基层科普与线上自助问诊需求增长，但通用聊天模型存在「胡编药名、忽略危急症状」等风险。本课程小组以「类蚂蚁阿福」体验为目标，建设**青禾门诊智能问诊系统**：在教学演示场景下，完成症状采集、知识检索增强生成、安全门禁与就诊卡辅助，形成可运行、可讲解、可测试的软件系统，而非一次性脚本。

系统明确声明：**不替代面诊，不做真实处方与医保结算**。

## 1.2 问题陈述

| 编号 | 问题 | 若不解决的后果 |
| --- | --- | --- |
| P1 | 用户不会一次说清病情 | 无法形成可用的参考建议 |
| P2 | 大模型可能编造药品与剂量 | 演示也不安全、不可信 |
| P3 | 胸痛等危急情况若继续「开方案」 | 违背安全底线 |
| P4 | 知识与会话无沉淀 | 无法体现系统级工作量 |
| P5 | 组件（模型/检索）可能宕机 | 演示中断、体验差 |

## 1.3 建设目标

1. 提供完整问诊主流程：开会话 → 多轮对话 → 参考诊断/处理建议 → 历史可回看。  
2. 知识有据：回答前经 RAG 检索，并展示出处线索。  
3. 安全可控：红旗拦截 + 药品白名单，门禁不可关闭。  
4. 系统可降级：模型或检索不可用时仍可演示且不崩溃。  
5. 具备就诊卡、知识库浏览/补充、语音与图片辅助输入等周边能力，体现「软件系统」体量。

## 1.8 成功标准（验收口径）

1. 至少三条演示剧本可复现：普通上感出方案、过敏含禁忌提示、红旗只急诊。  
2. 关掉部分检索组件或模型时，系统可降级演示且不崩溃。  
3. 展示药品均可在白名单中查到，并尽量带出处。  
4. 报告能说清：主流程、检索架构、降级阶梯、安全门禁。  
5. 非合理输入（空内容、过期会话、红旗否定句等）有明确处理策略。

# 第 2 章 概要设计

## 2.1 设计原则

1. **单 Agent + 工具**：一个大模型主脑负责追问与生成；RAG 是工具，不是并列业务线。  
2. **串行主链路**：理解 → 检索 → 生成 → 门禁，避免「三路并行」误解。  
3. **安全后置且强制**：门禁在 LLM 输出之后，红旗与白名单不可降级关闭。  
4. **组件可缺席**：检索与模型可降级，系统「变笨不能变危险」。  
5. **前后端分离**：React 负责交互与展示；Spring Boot 负责编排、持久化与安全。

## 2.2 逻辑架构

```text
┌──────────────────── 表现层（web） ────────────────────┐
│  问诊页 │ 就诊卡页 │ 知识库页 │ 历史侧栏 │ 流式卡片展示  │
└───────────────────────┬───────────────────────────────┘
                        │ HTTP / SSE（/cs-api 代理）
┌───────────────────────▼───────────────────────────────┐
│                 应用层（agent-server）                  │
│  ConsultController · Profile · Kb · Media · Session    │
│  ConsultOrchestrator（单 Agent 编排）                  │
└───────────┬───────────────────────────┬───────────────┘
            │                           │
┌───────────▼───────────┐   ┌───────────▼───────────────┐
│ 领域层（domain）       │   │ 外部能力                   │
│ 门禁 SafetyGate        │   │ LLM（OpenAI 兼容）         │
│ 就诊卡 / 会话 / 消息   │   │ RAG：Chroma/ES/Qdrant/图谱 │
│ 药品白名单 / 红旗词    │   │ 语音听写 / 视觉观察         │
└───────────┬───────────┘   └───────────────────────────┘
            │
┌───────────▼───────────┐
│ MySQL 8 持久化底账     │
└───────────────────────┘
```

## 2.4 模块划分

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| M1 知识底账与导入 | 病药主数据、科普切段、出处 | 不对用户直接说话 |
| M2 RAG 检索门面 | `retrieve(query)`；混合检索与 RRF 融合；降级 | 不生成最终话术 |
| M3 安全门禁 | 红旗、药白名单、否定语处理 | 不替代 RAG |
| M4 问诊编排 | 单 Agent：追问、调 RAG、生成草稿、过门禁 | 不绕过门禁 |
| M5 就诊卡 | 多卡 CRUD、问诊关联、摘要注入 | 不做诊断 |
| M6 多媒体 | 图片存储与观察、语音转写 | 不自动开药 |
| M7 知识库前台 | 浏览、检索、运营补录 | 不关红旗 |
| M8 前端壳 | 青禾 UI、历史管理、SSE 消费 | 不写医学规则 |

依赖顺序：`M1 → M2 → M3 → M4`；`M5/M6/M7` 并行增强；`M8` 对接全部应用接口。

## 2.5 核心业务流程（概要）

```text
用户输入
  →（可选）Java 快速红旗扫描
  → LLM：判断追问或作答；知识不足则发起 RAG
  → RAG：向量 / 关键词 / 图谱取片段并融合
  → LLM：基于「用户信息 + 片段」生成结构化草稿
  → Java 门禁：红旗？药在白名单？文案是否安全？
  → 通过：返回卡片；不通过：改写为就医建议 / 转人工提示
```

# 第 3 章 详细设计

## 3.1 问诊编排详细设计

### 3.1.1 类职责

| 类 / 组件 | 职责 |
| --- | --- |
| `ConsultController` | REST/SSE 入口；会话 CRUD、消息、上下文、中断恢复 |
| `ConsultOrchestrator` | 一轮问诊任务编排与状态视图 |
| `ConsultWorkflow` / `ConsultSupport` | 图节点或步骤：摄入、检索、生成、门禁、记忆 |
| `ConsultHistoryService` | 历史列表标题、删除、重命名、批量删除 |
| `RagFacade` | 统一检索入口，屏蔽底层索引差异 |
| `SafetyGate` | 红旗与药品校验；否定语解除 |

### 3.1.2 一轮消息时序

```text
前端                Controller           Orchestrator          RAG/LLM/门禁
 |  POST messages(SSE) |                    |                    |
 |-------------------->| 校验会话           |                    |
 |                     |------------------->|                    |
 |                     |                    |--红旗预检--------->|
 |                     |                    |--需要则 retrieve-->|
 |  event:retrieving   |<-------------------|<--hits-------------|
 |  event:generating   |<-------------------|--LLM 起草---------|
 |                     |                    |--SafetyGate-------|
 |  event:result(card) |<-------------------|<--通过/改写--------|
 |  complete           |                    |                    |
```

### 3.1.3 结果卡片字段

| 字段 | 含义 |
| --- | --- |
| `diagnoses` | 可能诊断（参考） |
| `plan` | 处理建议 |
| `drugs` | 白名单内用药参考 |
| `evidences` | RAG 命中出处 |
| `redFlag` | 是否危急出口 |
| `degraded` | 是否降级模式 |
| `disclaimer` | 教学免责声明 |
| `memory` / `chronicCaution` | 记忆与慢病提示（若有） |

## 3.2 安全门禁详细设计

### 3.2.1 红旗策略

1. 扫描用户文本中的危急模式（胸痛、冷汗、大出血、叫不醒等）。  
2. 若同句或近邻出现否定解除语（「不存在了」「没有了」「没了」等），则该红旗解除。  
3. 「和 / 与」连接的并列症状可一并解除。  
4. 命中且未解除：直接返回急诊建议，**不生成药品**。  

### 3.2.2 药白名单策略

1. LLM 草稿中的药品名与 `med_drug`（或等价白名单）比对。  
2. 未命中：剔除或改写为就医建议。  
3. 用法/禁忌优先采用库内文案，禁止模型自由剂量发挥。  

## 3.3 RAG 检索详细设计

### 3.3.1 检索通道（可配置）

| 通道 | 作用 | 关闭时 |
| --- | --- | --- |
| 向量（如 Chroma） | 语义相近科普段 | 走关键词/图谱/底账 |
| ES | 药名、标准症状、红旗词精确匹配 | 走向量/底账 |
| 图谱（Neo4j） | 病-症-药关系补充 | 忽略图谱命中 |
| MySQL 底账 | 最终兜底与元数据 | 核心数据仍需可用 |

### 3.3.2 融合

多路命中经 RRF（或等价融合）排序后截取 Top-K，拼入 Prompt。对 LLM 而言始终是一次「检索工具」调用。

## 3.4 会话与历史详细设计

### 3.4.1 会话实体要点

- `cs_session`：买家、店铺名（门诊智能助手）、状态、更新时间。  
- `title`：用户自定义标题；为空时用首条用户消息截断生成展示标题。  

### 3.4.2 历史操作

| 操作 | 接口 | 行为 |
| --- | --- | --- |
| 列表 | `GET /sessions` | 按更新时间倒序 |
| 重命名 | `PATCH /sessions/{id}` `{title}` | 校验非空，最长约 40 字 |
| 删除 | `DELETE /sessions/{id}` | 清消息、任务、痕迹、会话级记忆 |
| 多选删除 | `DELETE /sessions` `{ids:[]}` | 循环安全删除 |

前端侧栏：三点菜单 → 重命名 / 多选 / 删除；多选模式底部条批量删除。

## 3.5 就诊卡详细设计

| 能力 | 设计要点 |
| --- | --- |
| 多卡 | 同一 `user_id` 允许多行；启动修复历史唯一索引 |
| 字段 | 姓名、基础体征、过敏史、手术史、家族史等（演示级） |
| 关联问诊 | `PUT .../context` 写入 `profileId` / `profileLinked` |
| 注入 | 问诊摘要简报进入 Prompt，**不做诊断** |
| 回写 | 问诊结束后可按策略更新档案摘要 |

## 3.6 多媒体详细设计

| 能力 | 约束 |
| --- | --- |
| 图片 | jpeg/png/gif/webp，≤8MB；存本地；视觉模型只描述可见体征 |
| 语音 | 浏览器采集 16kHz WAV；本机听写；结果填输入框，不自动发送 |
| 合成发送 | `text` + `imageIds`；二者皆空拒绝 |

## 3.7 前端页面详细设计

| 页面 | 关键组件 / 行为 |
| --- | --- |
| 问诊 | `ConsultPage`：侧栏历史、SSE 对话、欢迎卡、输入区、就诊卡抽屉 |
| 就诊卡 | `ProfilePage`：表单编辑、多卡列表、跳转问诊 |
| 知识库 | `KbPage`：分类、检索、详情、补录 |
| 公共 | `HistorySideList`、Markdown 卡片、青禾主题 CSS |

响应式：宽度 <800px 时历史侧栏改为抽屉遮罩。

## 3.8 异常与非合理输入处理设计

| 输入 / 场景 | 期望行为 |
| --- | --- |
| 文本与图片皆空 | 400/业务错：提示先描述或上传 |
| localStorage 会话已删 | 识别「会话不存在」，清本地号并重建后重发 |
| 红旗肯定句 | 急诊出口，无 drugs |
| 红旗否定句 | 解除后继续常规问诊 |
| 模型/检索失败 | `degraded` 提示，安全收尾，不 500 |
| 超大图片 | 上传拒绝 |
| 重命名空标题 | 拒绝，提示不能为空 |

## 3.9 数据库主要表（逻辑）

| 表 | 用途 |
| --- | --- |
| `cs_session` | 会话 |
| 消息表 | 对话内容 |
| `cs_health_profile` | 就诊卡 |
| `med_*` | 病症药、方案、红旗、切段 |
| 任务 / 痕迹 / 记忆表 | 可恢复任务与可解释链路 |

2. **安全设计意识**：医疗场景下「能回答」不如「答得安全」；门禁与白名单是系统级能力。  
3. **LLM 工程化**：单 Agent + RAG 工具比空聊更可控；降级保证演示可用性。  
4. **工程排障**：过期会话、索引残留、红旗否定等真实缺陷的定位与修复。  

## 6.4 遇到的问题与解决

| 问题 | 解决思路 |
| --- | --- |
| 早期商城方向偏离课程目标 | 收敛为门诊问诊，废弃商城文档主线 |
| 组件繁多导致讲解不清 | 统一叙事：LLM→RAG→门禁串行 |
| Hibernate 不删旧唯一索引 | 启动时 schema 修复 |
| 历史列表被压扁 | 固定行高 + 滚动容器 |
| 删除按钮体验差 | 改为 DeepSeek 式三点菜单 |

## 6.5 不足与展望

1. 病种与知识覆盖仍以演示包为主，可继续扩充。  
2. 前端自动化 E2E 不足。  
3. 可解释链路页若时间允许可再强化可视化。  
4. 多用户登录与权限未做（课程演示采用固定演示用户）。  

## 6.6 对评分标准的自检

| 评分点 | 自检结论 |
| --- | --- |
| 功能丰富、是系统 | 多子系统联动，非单文件程序 |
| 运行流畅、抗非合理输入 | 空输入、过期会话、红旗否定等已处理 |
| 测试完备合理 | 有自动化清单 + 场景用例 + Bug 回归 |
| 汇报表达 | 见附录 PPT 提纲与剧本 |
| 报告规范 | 六章齐全，可合订提交 |

# 附录 A 课堂演示剧本

> 建议总时长 8～12 分钟：演示 6～8 分钟 + 提问。

## 剧本 1｜普通上感（展示主链路）

1. 打开系统，介绍「青禾门诊 · 教学参考」。  
2. 点击「开启新对话」。  
3. 输入：「喉咙痛，低烧两天」。  
4. 若系统追问，简短补充：不发烧很高、无胸痛。  
5. **讲解点**：LLM 理解 → RAG 取知识 → 门禁校验 → 卡片含建议与免责声明。  

## 剧本 2｜红旗急诊（展示安全）

1. 新对话输入：「突然胸口疼，出冷汗」。  
2. **讲解点**：不诊断、不开药，只导向急诊；门禁不可关闭。  

## 剧本 3｜红旗否定（展示非合理/纠错输入）

1. 承接或新开后说明：用户更正病情。  
2. 输入含「胸口疼……不存在了，其实是嗓子疼」。  
3. **讲解点**：系统能解除误触发红旗，体现输入鲁棒性。  

## 剧本 4｜就诊卡 + 历史（展示系统完整性）

1. 打开就诊卡，展示多卡 / 关联。  
2. 回到问诊，打开历史三点菜单：重命名或说明多选删除。  
3. **讲解点**：这是完整软件系统能力，不只是「聊一句」。  

## 可选加分项

- 上传一张皮疹/喉咙相关图片，说明「只观察体征，仍过门禁」。  
- 关闭某检索组件后提问，展示降级不崩溃。

# 附录 B PPT 汇报提纲（建议 8～10 页）

| 页 | 标题 | 内容要点 |
| --- | --- | --- |
| 1 | 封面 | 项目名、组名、成员、课程 |

### 汇报表达建议

1. 先讲「用户故事」再讲技术，避免一上来堆组件名。  
2. 架构图只保留一条主箭头：问诊→检索→生成→门禁。  
3. 被问「是不是套壳 ChatGPT」时：回答有 RAG 依据、白名单、红旗、会话与就诊卡等系统能力。  
4. 被问「能不能真看病」时：明确教学演示、非诊疗。
